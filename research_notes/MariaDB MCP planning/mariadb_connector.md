# MariaDB Connector/Python connectivity and test practices

## Which Connector/Python installation mode/version and supported Python/platform matrix best fits native Windows, Linux, and macOS use?

### Takeaway

For a production release today, pin the latest stable 1.1 release (the current docs identify 1.1.14) and account for its mandatory native MariaDB Connector/C dependency in each OS installer. Connector/Python 2.0's pure-Python mode or bundled binary wheels are much easier to deploy across Windows/Linux/macOS, but the official docs still label 2.0.0rc2 a Release Candidate, so treat it as an evaluation path rather than a production default until GA.

### Cited Findings

- MariaDB's current guide identifies Connector/Python 1.1.14 as the most recent release; 1.1 is the stable/GA series and the 2.0 series is still an RC (2.0.0rc2). — [Connector/Python guide](https://mariadb.com/docs/connectors/mariadb-connector-python/mariadb-connector-python-guide); [Installation](https://mariadb.com/docs/connectors/mariadb-connector-python/install)
- The current guide lists CPython 3.9 through 3.14 for 1.1, and CPython 3.10 or later for 2.0. The separate install page says 2.0 supports Python 3.10+, and source-build prerequisites state Python 3.10 minimum (and say 1.1 requires Python 3.8). — [Connector/Python guide](https://mariadb.com/docs/connectors/mariadb-connector-python/mariadb-connector-python-guide#requirements); [Installation](https://mariadb.com/docs/connectors/mariadb-connector-python/install#prerequisites)
- The published Python-version statements are not fully consistent for 1.1: the current guide says CPython 3.9–3.14, while the install page's C-extension prerequisite says 1.1 requires Python 3.8. Validate the exact release's package metadata/wheels against the project's chosen Python versions rather than treating either wording as a precise compatibility guarantee. — [Connector/Python guide](https://mariadb.com/docs/connectors/mariadb-connector-python/mariadb-connector-python-guide#requirements); [Installation](https://mariadb.com/docs/connectors/mariadb-connector-python/install#c-extension-build-prerequisites)
- Version 1.1 always installs the C extension, requires MariaDB Connector/C preinstalled, does not provide pure-Python or binary-wheel installation, and includes connection pooling. MariaDB Connector/C 3.3.1 or later is required. — [Installation](https://mariadb.com/docs/connectors/mariadb-connector-python/install#installing-version-1.1-stable-ga)
- Version 2.0 provides a pure-Python default (`pip install --pre mariadb`), a C extension (`mariadb[c]`), and precompiled binary wheels (`mariadb[binary]`). The pure-Python implementation claims compatibility with CPython, PyPy, and all Python interpreters without compiler/system dependencies; binary wheels bundle Connector/C, need no compiler, and are available for “common platforms” including Windows, Linux, and macOS. The docs do not enumerate exact OS releases or CPU architectures for those wheels. — [Installation](https://mariadb.com/docs/connectors/mariadb-connector-python/install#installation-options)
- A plain `pip install mariadb` selects stable 1.1; `--pre` is required to select 2.0, and MariaDB says not to use non-GA releases in production. — [Installation](https://mariadb.com/docs/connectors/mariadb-connector-python/install#installing-version-2.0-release-candidate)
- In 2.0, implementation can be chosen with `MARIADB_PYTHON_CONNECTOR` (`c`, `binary`, or `python`); unset, the connector tries C, then binary, then pure Python. — [Connection API](https://mariadb.com/docs/connectors/mariadb-connector-python/api/connection#implementation-selection)

### Inferences

- **Recommended production baseline:** pin `mariadb==1.1.14` and package/document MariaDB Connector/C 3.3.1+ for all three native OS targets; CI should exercise Windows, Linux, and macOS install and connect paths. This trades installer simplicity for a stable GA API. This recommendation follows the release status and installation requirements above. — [Installation](https://mariadb.com/docs/connectors/mariadb-connector-python/install)
- **Potential next-generation distribution:** test 2.0 pure Python first where avoiding per-platform Connector/C deployment is more important, or use `mariadb[binary]` if native performance is needed and the target wheel exists. Keep it opt-in until the RC becomes GA; test the precise Python/OS/architecture combinations because “common platforms” is not a complete support matrix. — [Installation](https://mariadb.com/docs/connectors/mariadb-connector-python/install#installation-options)

### Gaps

- Official installation documentation does not give a complete 2.0 binary wheel matrix by OS version, CPU architecture, or Python ABI. Confirm wheel availability for each supported build target during packaging.
- Docs differ on the minimum Python version wording for Connector/Python 1.1. Verify the exact 1.1.14 package metadata and supported interpreter matrix before publishing a formal support claim.

## Which connector APIs/options support connection/read/write timeouts, cursor cleanup, transactions/autocommit, and safe result iteration? What are the limitations around cancellation?

### Takeaway

Set explicit bounded connect/I/O/query limits, use context managers or `finally` to close cursors and connections, and explicitly choose buffered versus streaming results. The connector exposes a `query_timeout` option, but the docs do not clearly state its implementation parity across 2.0 backends, and they document no general-purpose query-cancel API; do not treat task cancellation or a socket timeout as proof that server work stopped.

### Cited Findings

- `connect_timeout` (seconds; default 10) bounds initial connection establishment. `socket_timeout` bounds socket I/O and is the primary timeout for pure Python. `read_timeout` and `write_timeout` are explicitly marked C-extension-only; on pure Python they map to `socket_timeout`. `query_timeout` is an integer maximum query execution time in seconds, with zero meaning no timeout. — [Connection API: timeout parameters](https://mariadb.com/docs/connectors/mariadb-connector-python/api/connection#timeout-parameters)
- The connection API lists `read_only` as a connection parameter and `autocommit` defaults to `False`. It describes commit/rollback and says closing a connection with uncommitted changes implicitly rolls them back. — [Connection API](https://mariadb.com/docs/connectors/mariadb-connector-python/api/connection); [Transactions](https://mariadb.com/docs/connectors/mariadb-connector-python/transactions-with-mariadb-connector-python)
- MariaDB Connector/Python's usage guide recommends freeing resources and closing cursors/connections; connection and cursor APIs document context managers and explicit `.close()`. Cursor `.close()` frees resources; connection `.close()` makes the connection and its cursors unusable. — [Basic Usage](https://mariadb.com/docs/connectors/mariadb-connector-python/usage); [Cursor API](https://mariadb.com/docs/connectors/mariadb-connector-python/api/cursor#cursorclose); [Connection API](https://mariadb.com/docs/connectors/mariadb-connector-python/api/connection#connectionclose)
- Cursor docs describe `buffered=False` as streaming results row-by-row with lower memory use, but the connection remains occupied until rows are consumed and only one unbuffered cursor can be active on a connection. `fetchone()`, `fetchmany()`, and cursor iteration are available. Buffered results use more memory but free the connection after execution. — [Cursor API](https://mariadb.com/docs/connectors/mariadb-connector-python/api/cursor#cursorbuffered-bool)
- The cursor documentation is internally inconsistent about the default buffering mode: its parameter listing says `buffered=True` by default, while its basic cursor example labels the default cursor unbuffered. Explicitly pass `buffered=True` or `False` rather than relying on a default. — [Cursor API](https://mariadb.com/docs/connectors/mariadb-connector-python/api/cursor)
- `Connection.kill(connection_id)` asks the server to kill a connection, but requires `SUPER` or `CONNECTION ADMIN`; those are inappropriate privileges for the proposed read-only MCP account. The connection API does not document a lower-privilege per-query cancellation method. — [Connection API: `kill`](https://mariadb.com/docs/connectors/mariadb-connector-python/api/connection#connectionkillconnection_id-int-none)
- MariaDB server-side `max_statement_time` can abort statements, including via `SET STATEMENT max_statement_time=... FOR SELECT ...`, but its timeout is checked intermittently at execution checkpoints and may exceed the configured limit. — [Aborting statements](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/query-optimizations/aborting-statements); [Query limits and timeouts](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/query-optimizations/query-limits-and-timeouts)
- Version 2.0 documents native async APIs (`asyncConnect`, async cursors, async pools) for both pure-Python and C implementations, including async context managers. The cited async docs do not describe what happens to an in-flight server query if the awaiting task is cancelled. — [Async/Await Support](https://mariadb.com/docs/connectors/mariadb-connector-python/async-usage)
- Version 2.0 defaults TLS on and certificate verification on; the 1.1 C extension defaults TLS and certificate verification off. `ssl`, `ssl_ca`, and `ssl_verify_cert` are documented options. — [Connection API: SSL/TLS parameters](https://mariadb.com/docs/connectors/mariadb-connector-python/api/connection#ssltls-parameters)

### Inferences

- Set explicit, configurable `connect_timeout`, `socket_timeout` (or `read_timeout`/`write_timeout` only when intentionally using the C implementation), and a nonzero query bound. Test the chosen values against every supported connector implementation because docs advertise `query_timeout` but do not clearly mark its backend support, units of precision, or cancellation semantics.
- Treat socket I/O timeouts as transport bounds, not server-side cancellation. If a blocking request times out or is cancelled while streaming, avoid reusing that connection unless protocol/result state is known to be clean; closing it is the conservative cleanup path. The API docs explain pending/unbuffered results and connection close behavior but do not promise that closing promptly interrupts all server work.
- For an MCP service that is read-only, `autocommit=True` is a reasonable default to avoid a lingering transaction between independent reads; alternatively explicitly `rollback()`/close in a `finally` block. Database grants—not the connector's `read_only=True` setting—should be the security boundary.
- Use small/bounded result sets with explicit `buffered=True`; use explicit `buffered=False` plus row-by-row iteration for potentially large results, and apply row/result limits in the server-side SQL layer. Do not fetch an unbounded result into memory merely because it is a read query.
- Prefer context-managed, request-scoped connection/cursor lifetimes initially. Add a pool only if concurrency/connection setup measurements justify it; pool acquisition and shutdown then need explicit lifecycle ownership.
- For TLS on 1.1, explicitly require TLS and verify the server certificate using the intended CA (`ssl=True`, `ssl_verify_cert=True`, `ssl_ca=...`) rather than inheriting the insecure C-extension defaults. Do not disable verification to work around certificate deployment issues.

### Gaps

- Connector docs do not clearly say whether `query_timeout` is honored identically by C, binary-wheel, and pure-Python implementations; neither do they describe cancellation guarantees, timeout error classes, or whether server execution is stopped after the client I/O times out.
- The 2.0 async docs describe async operations but not cancellation/shutdown semantics for in-flight queries. Avoid promising prompt cancellation absent implementation-specific tests or upstream clarification.
- Cursor documentation conflicts on the buffering default; use explicit values and pin/test a connector release.

## What minimum MariaDB grants support required metadata discovery and read queries, and how should integration tests avoid requiring Docker for unit tests?

### Takeaway

Use a dedicated non-root account with only `SELECT` on the intended schema, scoped to the client host, and do not add global `SHOW DATABASES`, `PROCESS`, `SUPER`, or grant-option privileges unless a demonstrated feature needs them. Keep the normal test suite entirely offline with unit tests/mocks; make database integration tests an explicitly enabled optional tier against a developer/CI MariaDB service or disposable schema, with teardown isolated from the runtime read-only account.

### Cited Findings

- MariaDB defines `SELECT` as the privilege needed to read table data and supports granting it at the database level (`db_name.*`), table level, or column level. Database-level privileges apply to all current and future tables/functions in that database. — [GRANT: privilege levels and SELECT](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant#database-privileges); [GRANT: table privileges](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant#table-privileges)
- `SHOW TABLES` lists a schema's tables/views but omits base tables or views on which the account has no privileges. MariaDB also identifies `information_schema.TABLES` as a source of table information. — [SHOW TABLES](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/show/show-tables)
- `information_schema.COLUMNS` exposes column name, type, nullability, order, defaults, and other metadata. Its `PRIVILEGES` field describes privileges held for the column. — [Information Schema COLUMNS](https://mariadb.com/docs/server/reference/system-tables/information-schema/information-schema-tables/information-schema-columns-table)
- Without global `SHOW DATABASES`, that statement returns only databases containing tables on which the account has some privilege; global `SHOW DATABASES` permits seeing all databases. — [GRANT: SHOW DATABASES](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant#show-databases); [SHOW DATABASES](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/show/show-databases)
- `SHOW CREATE VIEW` requires both `SHOW VIEW` and `SELECT` on that view. — [SHOW CREATE VIEW: grants](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/show/show-create-view#grants)
- `PROCESS` exposes active process information; `SUPER` and `CONNECTION ADMIN` provide administration capabilities, including killing other users' connections. These are not normal read-query privileges. — [GRANT: PROCESS](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant#process); [GRANT: CONNECTION ADMIN](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant#connection-admin)
- `CREATE USER` supports host-scoped account names and `REQUIRE SSL`; GRANT syntax also allows TLS requirements and resource limits such as `MAX_USER_CONNECTIONS` and `MAX_STATEMENT_TIME`. — [CREATE USER](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/create-user); [GRANT](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant)
- The Connector/Python source package's own integration tests accept connection settings via `TEST_DB_USER`, `TEST_DB_PASSWORD`, `TEST_DB_DATABASE`, `TEST_DB_HOST`, and `TEST_DB_PORT`; their documented defaults include user `root`, illustrating test-suite configuration, not a suitable production account. — [Connector/Python Installation: Test suite](https://mariadb.com/docs/connectors/mariadb-connector-python/install#test-suite)
- pytest supports skipping a test when its external resource is unavailable, including by calling `pytest.skip()`, and supports `importorskip()` for optional dependencies. — [pytest: skip and xfail](https://docs.pytest.org/en/stable/how-to/skipping.html)
- pytest yield fixtures run teardown after the test and are suited to resource cleanup; pytest recommends separating state-changing setup into atomic fixtures so successful operations can be cleaned up even if later setup fails. — [pytest: fixtures and teardown](https://docs.pytest.org/en/stable/how-to/fixtures.html#teardown-cleanup-aka-fixture-finalization)
- pytest's `monkeypatch` fixture can set/delete environment variables and automatically undo those changes after the test/fixture, which supports tests of opt-in integration configuration without leaking process state. — [pytest: monkeypatch environment](https://docs.pytest.org/en/stable/how-to/monkeypatch.html#monkeypatching-environment-variables)

### Inferences

- **Minimal runtime grant for a configured schema:** `GRANT SELECT ON appdb.* TO 'mcp_ro'@'trusted-client-host';`. This should permit ordinary table reads and discovery of tables/columns in that schema, because SHOW TABLES visibility is privilege-filtered and the metadata tables expose the relevant schema. Validate queries against supported MariaDB server versions and actual views. Add `SHOW VIEW` only if the MCP feature uses `SHOW CREATE VIEW`; regular view reads still need `SELECT` on the view and its definer/security semantics should be assessed.
- Create a distinct account (not root), scope its host as narrowly as deployment allows, use a strong secret from the host's secret/config mechanism, require TLS for remote connections where supported, grant only the configured database, and omit `WITH GRANT OPTION`. Consider `MAX_USER_CONNECTIONS`/`MAX_STATEMENT_TIME` as server-side guardrails if acceptable for the server workload. Do not grant `SHOW DATABASES` simply to enumerate everything: prompt/configure the allowed schema and avoid disclosing unrelated database names.
- Make ordinary tests independent of Docker and MariaDB: unit-test connection-configuration validation, SQL policy/allow-listing, parameter binding, MCP request behavior, and error mapping with fake connector objects or monkeypatched connection factories. Do not import or connect to the real server from unit-test collection/setup.
- Mark live-server tests separately (e.g. `integration`), read an explicit test DSN/host/user/password from environment, and skip with a clear reason when absent. A separate CI job or local opt-in command can run those against an installed MariaDB service, a pre-provisioned CI service, or a user-chosen disposable database; Docker is only one possible provisioning method, not a unit-test prerequisite.
- For tests that need fixture data, provision an isolated schema/table with a separate setup/admin identity or a pre-provisioned schema; exercise actual reads with the same limited read-only account used by the MCP runtime. Keep teardown credentials out of application configuration. Prefer unique test schema/table names and fixture-managed cleanup; if tests cannot safely create/drop schemas themselves, make schema setup an explicit external step.
- Integration fixture teardown should close cursors/connections regardless of test result. If the fixture creates state, use separate yield fixtures per state-changing setup step so failures do not bypass cleanup. Keep credentials out of test logs and never reuse a production account.

### Gaps

- MariaDB docs document access filtering for `SHOW TABLES` and metadata table contents, but do not give a single canonical grant recipe for every possible metadata-discovery API (e.g. indexes, constraints, view definitions, routines, and server-specific information-schema tables). Test only the discovery queries the MCP actually implements and add privileges narrowly when required.
- The `EXPLAIN` reference explains its purpose but does not specify an independent privilege matrix. Validate `EXPLAIN SELECT` under the intended read-only grants on supported server versions; do not infer that profiling, `SHOW EXPLAIN FOR <other connection>`, or analysis commands require no additional privileges.
- pytest's official docs do not prescribe a MariaDB disposable-instance fixture or Docker strategy. The environment-gated integration and disposable-schema pattern above is a project recommendation composed from pytest's fixture/skip facilities and MariaDB's grant model, not a requirement imposed by pytest.
