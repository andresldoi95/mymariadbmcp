# MariaDB MCP Read-Only SQL Security

## Which maintained SQL parsers support MariaDB/MySQL dialects and expose ASTs suitable for whole-query authorization, and what are their limitations?

### Takeaway
For a Python MCP server, SQLGlot is the strongest readily usable general-purpose choice: it has a maintained, official MySQL dialect and traversable ASTs. For Go, TiDB's parser is a serious alternative with MySQL-compatible ASTs and visitors. Neither claims to be an exact MariaDB-version validator; parsing is only the syntax/structure stage, not authorization or semantic proof.

### Cited Findings
- SQLGlot's repository describes it as a SQL parser/transpiler, documents AST traversal and table/column discovery, and lists MySQL as an **Official** dialect (core-team-maintained at higher priority than community dialects). [SQLGlot repository](https://github.com/tobymao/sqlglot)
- SQLGlot explicitly warns that its parser is intentionally lenient, may accept queries a real engine rejects, and is a transpiler rather than a validator. It also says comments are preserved on a best-effort basis. [SQLGlot README: FAQ and examples](https://github.com/tobymao/sqlglot)
- SQLGlot's MySQL dialect implementation uses a MySQL tokenizer/parser, and recognizes `#`, `--`, and block comments plus MySQL-specific `@@` tokens; it is a MySQL dialect, not a MariaDB-specific dialect. [SQLGlot MySQL dialect](https://sqlglot.com/sqlglot/dialects/mysql.html)
- TiDB's parser README calls it a Go MySQL-compatible SQL parser, says it supports almost all MySQL features, and points to the parser grammar for details. Its quickstart says parsing yields an AST and demonstrates visiting nodes such as `SelectStmt`, `TableName`, and `ColumnName`. [TiDB parser README](https://github.com/pingcap/tidb/blob/master/pkg/parser/README.md); [TiDB parser quickstart](https://github.com/pingcap/tidb/blob/master/pkg/parser/docs/quickstart.md)
- The TiDB parser quickstart notes parser instances are not goroutine-safe, are not lightweight, and should be reused; it also requires a parser driver for basic data types. [TiDB parser quickstart](https://github.com/pingcap/tidb/blob/master/pkg/parser/docs/quickstart.md)

### Inferences
- Pin the parser version, choose its explicit MySQL dialect (never a permissive generic/superset dialect), and keep a MariaDB-version-specific regression corpus that parses and executes test cases against every supported server version. Treat parser errors, unknown AST node kinds, or unmodeled syntax as rejection.
- SQLGlot's MySQL parser is the pragmatic Python default, but avoid using AST parsing as proof that SQL is valid MariaDB or safe. A Go implementation can use TiDB's parser; expect some MariaDB-vs-MySQL compatibility gap and test it.
- Maintain a parser adapter that exposes statement kind, all query blocks, relation sources, expressions, function calls, comments, locking clauses, and output projections. Upgrade the parser only with review of AST-shape changes and adversarial tests.

### Gaps
- Neither project's documentation claims complete compatibility with MariaDB's versioned grammar, executable comments, or MariaDB-specific extensions. No source reviewed establishes a parser as a security authorization engine.

## What constructs should v1 reject or specially handle, particularly views, stored routines/functions, locking clauses, file access, user variables, and comments/multiple statements?

### Takeaway
Start with exactly one plain `SELECT` (plus a separately gated `EXPLAIN [FORMAT=JSON] SELECT` form). Reject syntax that writes, locks, changes session state, reaches files, invokes unreviewed executable code, or depends on behavior that the validator cannot model—including views and stored functions unless their full dependencies are explicitly resolved and authorized.

### Cited Findings
- MariaDB's `SELECT` grammar includes `INTO OUTFILE`, `INTO DUMPFILE`, `INTO var_name`, `FOR UPDATE`, `LOCK IN SHARE MODE`, and `PROCEDURE`; its description says SELECT also supports UNIONs, subqueries, and fully qualified cross-database names. [MariaDB SELECT](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/select)
- MariaDB documents `SELECT ... INTO OUTFILE` and `INTO DUMPFILE` as writing results to files; its `FILE` privilege allows server-side file reads/writes including `LOAD_FILE()` and `LOAD DATA INFILE`. [MariaDB SELECT](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/select); [MariaDB GRANT: FILE privilege](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant)
- MariaDB says `FOR UPDATE` and `LOCK IN SHARE MODE` acquire row locks; for non-transactional MyISAM/Aria tables these clauses can take table locks even with autocommit enabled. [MariaDB FOR UPDATE](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/for-update); [MariaDB LOCK IN SHARE MODE](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/lock-in-share-mode)
- MariaDB supports `#`, `-- `, and `/*...*/` comments, plus executable `/*!...*/` and `/*M!...*/` comments whose embedded SQL is executed by MariaDB (subject to version rules). [MariaDB Comment Syntax](https://mariadb.com/docs/server/reference/sql-statements/comment-syntax)
- MariaDB `PREPARE` documentation says a prepared SQL string must represent one statement; `?` markers bind values, not SQL keywords or identifiers. [MariaDB PREPARE](https://mariadb.com/docs/server/reference/sql-statements/prepared-statements/prepare-statement)
- MariaDB user variables are session-scoped, can be assigned with `:=` inside a statement or via `SELECT ... INTO`, and their read/write order within a statement is undefined. [MariaDB User-Defined Variables](https://mariadb.com/docs/server/reference/sql-structure/sql-language-structure/user-defined-variables)
- MariaDB view definitions may refer to base tables or other views, joins, UNIONs, subqueries, and stored functions. A view defaults to `SQL SECURITY DEFINER`; privileges on referenced objects at invocation are checked as the view creator or invoker according to its security mode. [MariaDB CREATE VIEW](https://mariadb.com/docs/server/server-usage/views/create-view)
- MariaDB stored functions also default to `SQL SECURITY DEFINER`. The `CONTAINS SQL`, `NO SQL`, `READS SQL DATA`, and `MODIFIES SQL DATA` characteristics are informative and MariaDB does not check that they are accurate; a function body can contain procedure statements, including writes. [MariaDB CREATE FUNCTION](https://mariadb.com/docs/server/reference/sql-statements/data-definition/create/create-function); [Stored Routine Privileges](https://mariadb.com/docs/server/server-usage/stored-routines/stored-functions/stored-routine-privileges)
- MariaDB `EXPLAIN` supports `SELECT`, `UPDATE`, and `DELETE`; `ANALYZE` executes the query, unlike EXPLAIN's plan-estimation operation. `EXPLAIN` can acquire metadata locks as SELECT does. [MariaDB EXPLAIN](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/analyze-and-explain-statements/explain)

### Inferences
- Allow only a single top-level `SELECT` AST with query-only child statements. Reject all DML/DDL/admin/transaction/session commands, `SELECT ... INTO` of any target, `PROCEDURE`, locking clauses, `HANDLER`, dynamic SQL, and any statement kind the parser adapter does not positively recognize. A semicolon may be accepted only as the sole trailing terminator after a lexer/parser confirms there is exactly one statement.
- Reject comment tokens entirely for v1—including ordinary comments, optimizer hints, and executable comments—using a MariaDB-aware lexer/token stream, not regex or comment-stripping followed by parse. Never validate one text and execute a differently normalized text. Executable comments can turn text hidden from a generic parser into active MariaDB SQL.
- Reject `@user` variables, `@@system` variables, `:=` assignments, `SELECT ... INTO`, and prepared-statement control syntax. Use driver-bound values for parameters; do not interpolate user values. Since parameter markers cannot stand for identifiers, database/table/column names must come from trusted configuration or be independently resolved and allowlisted.
- Reject stored procedures and all function calls not on a conservative built-in allowlist. In particular, reject stored/UDF calls, `LOAD_FILE`, lock/sleep/resource functions, and functions whose identity or side effects cannot be proven. Do not trust routine declarations such as `READS SQL DATA` as proof of safety.
- Reject views in v1 unless a controlled resolver expands each view's definition recursively and authorizes its transitive base tables, columns, and functions; also account for `DEFINER` privilege context and nested views. The simplest fail-closed v1 policy is base tables only. If views are later supported, restrict to reviewed views (prefer invoker security) and detect changes to definitions.
- For EXPLAIN, accept only an explicit allowlisted shape such as `EXPLAIN [FORMAT=JSON] <authorized SELECT>`; run the identical full validator over the nested SELECT. Reject `EXPLAIN UPDATE/DELETE`, `EXPLAIN table`, `EXPLAIN FOR CONNECTION`, `ANALYZE`, and other extensions in v1. Treat EXPLAIN as a query requiring timeout and metadata-lock controls.

### Gaps
- The exact set of built-in MariaDB functions that are side-effect-free is not enumerated here; a reviewed allowlist must be developed against the supported server versions. Parser behavior for MariaDB executable comments should be tested directly for the selected parser version.

## How should allowlists be enforced across joins, nested queries, CTEs, unions, aliases, views, and columns?

### Takeaway
Authorization must be scope-aware and recursive over the entire AST, not just the outer SELECT list. Resolve every table reference to an actual catalog object and every column reference to a source column in its query scope; deny unresolved, ambiguous, dynamic, or wildcard references unless they can be safely expanded against authoritative schema metadata.

### Cited Findings
- MariaDB SELECT explicitly permits UNIONs, subqueries, joins, fully qualified `db.table` references, and columns qualified by table or database/table; it permits `*` and `table.*`. [MariaDB SELECT](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/select)
- MariaDB column-level SELECT privileges constrain access not only in the select list but also in `WHERE`, `ON`, `GROUP BY`, and `ORDER BY`. [MariaDB GRANT: Column Privileges](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant)
- MariaDB CTEs act as query-local named result sets; recursive CTEs refer to themselves and repeatedly execute a subquery. [MariaDB CTEs](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/common-table-expressions)
- MariaDB view definitions can reference other views and base tables, and can contain joins, UNIONs, and subqueries; view privilege context can be DEFINER or INVOKER. [MariaDB CREATE VIEW](https://mariadb.com/docs/server/server-usage/views/create-view)

### Inferences
- Build a resolver with lexical query scopes. In every SELECT/UNION branch and nested SELECT, enumerate all FROM/JOIN relations, derived tables, CTE definitions/references, and correlated outer references; map aliases to resolved objects and output columns. A CTE alias is not a database table: authorize the CTE's defining query and then resolve its exposed columns. Treat each UNION arm as its own query scope and verify all arms.
- Validate every relation against an explicit database/schema/table allowlist, including qualified cross-database names. Fix the connection's default database and reject `USE`; treat omitted qualifiers as that fixed database. Deny system schemas (`mysql`, `information_schema`, `performance_schema`, `sys`) unless an explicit product feature separately authorizes them.
- Resolve each identifier against live or versioned catalog metadata using server-compatible identifier/case rules. For columns, inspect references in projections, predicates, joins, grouping, ordering, HAVING, window expressions, and nested expressions. Reject ambiguous/unqualified names that cannot be bound unambiguously. Check the policy on underlying columns even when the query refers to a permitted alias or derived-table/CTE output.
- Reject `*` and `table.*` where a column allowlist applies unless the resolver expands them from current schema metadata and checks every expanded column; fail if metadata is incomplete or stale. Also guard against schema-change races by using a consistent metadata snapshot or revalidating immediately before execution.
- Restrict expression functions by function-name resolution: do not assume every syntactically function-like call is built-in. Resolve database-qualified functions against routines/UDF catalogs (or deny all non-allowlisted calls), because stored functions can have a different security context and body than the SQL AST reveals.
- Keep parser-level policy and database grants as independent layers: application allowlists enforce narrower MCP policy, while a dedicated MariaDB account with only necessary SELECT grants limits damage if application validation errs. Include column-level SELECT grants where needed and avoid broad/global grants, roles, or grant options that defeat the intended boundary.

### Gaps
- MariaDB identifier case and name-resolution behavior depends on server configuration and SQL mode. A resolver needs exact supported server versions/configuration and differential tests; generic parser metadata helpers alone are not proof of MariaDB name binding.
- No source reviewed specifies a ready-made MariaDB AST resolver that enforces all schema/table/column policies across correlated queries, CTEs, views, and MariaDB semantics. This is application logic that needs adversarial testing.

## How should parser validation combine with database grants, identifier resolution, parameterization, result limits, timeouts, and EXPLAIN requests?

### Takeaway
Use layered enforcement: strict single-statement AST validation and catalog-based policy, a least-privilege MariaDB account as a backstop, bound parameters for values, and server-side execution/result budgets. Neither `read_only` nor a parser alone provides the required guarantee.

### Cited Findings
- MariaDB supports privileges at global, database, table, and column levels; `SELECT` is a read privilege, `FILE` enables file access, and `EXECUTE` enables stored routines. `SHOW GRANTS` reports grants for an account. [MariaDB GRANT](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant)
- From MariaDB 10.11, `READ_ONLY ADMIN` can write despite `read_only=ON` and change the global `read_only` setting; before 10.11 it was included in `SUPER`. `SUPER` itself permits write operations despite `read_only` in older/relevant versions and has been split into finer privileges from MariaDB 11.0. [MariaDB GRANT: READ_ONLY ADMIN and SUPER](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant)
- MariaDB parameter markers are for values in expression positions, not identifiers; prepared SQL text represents only one statement. [MariaDB PREPARE](https://mariadb.com/docs/server/reference/sql-statements/prepared-statements/prepare-statement)
- MariaDB supports `max_statement_time` to limit query execution time; the docs show applying it to a query with `SET STATEMENT ... FOR`. [MariaDB SET STATEMENT](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/set-commands/set-statement); [MariaDB SELECT](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/select)
- MariaDB `LIMIT` restricts returned rows, while EXPLAIN is a plan estimate and ANALYZE actually executes the statement. [MariaDB SELECT](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/select); [MariaDB EXPLAIN](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/analyze-and-explain-statements/explain)

### Inferences
- Configure a dedicated service principal with only `SELECT` on explicitly allowed tables/columns and no global privileges, `FILE`, `EXECUTE`, `CREATE ROUTINE`, write/DDL privileges, `GRANT OPTION`, `SUPER`, `READ_ONLY ADMIN`, or unrelated admin powers. Audit effective active roles and inherited grants—not only the direct grant rows—and make this account distinct from metadata/admin credentials. Keep server `read_only` as extra defense, not as the primary control.
- Resolve and authorize all object/column names before execution, then execute through the same connection identity and fixed default database. Re-check on catalog changes; database grants and app allowlists should agree. Avoid granting the MCP account `SHOW VIEW` or broad metadata access solely for convenience; use a separate trusted metadata path if necessary.
- Use connector/server prepared-statement binding for all value parameters. Never interpolate user values, and never attempt to bind identifiers; select identifiers only from a trusted allowlist or parse-and-resolve them as identifiers.
- Enforce a server-side statement deadline (for example, a deployment-controlled `max_statement_time` setting) and driver/network cancellation deadline. Do not let user SQL set its own timeout or session variables. Apply a maximum result-row count and byte-size cap; if the server may continue producing rows after the client stops fetching, cancel/close the statement or use a safely constructed server-side row cap. A row cap limits output, not necessarily scan/CPU cost, so retain execution-time and concurrency limits.
- For result limiting, v1 may require a bounded literal/parameter `LIMIT` or safely add a hard server-side limit only when a semantics-preserving query transformation is proven. Do not blindly wrap/rewrite arbitrary UNION, ordering, or nested queries. Enforce response bytes and cancel when caps are reached.
- For EXPLAIN requests, use an AST-level wrapper path: validate the EXPLAIN mode, authorize the inner SELECT exactly as a normal request, execute only after the validation succeeds, and apply time/deadline controls. Avoid exposing EXPLAIN FOR CONNECTION or ANALYZE, which are a different operation and ANALYZE executes the query.
- Test deny cases alongside allowed cases: writes hidden in CTEs/UNIONs, secondary database references, unauthorized predicate/join columns, stars, aliases, comments/executable comments, multiple statements, file functions, routines, locking modifiers, and EXPLAIN wrappers. Fail closed on parse errors, unknown nodes, unresolved identifiers, metadata errors, and timeout-control failures.

### Gaps
- The reviewed MariaDB documentation does not define a universal result-byte limit, connector cancellation behavior, or exact semantics of all driver prepared-statement implementations; select and test the actual driver/server combination. `max_statement_time` availability/configuration should be verified for each supported MariaDB release.
