# Database write operations: primary-source findings

Research snapshot: 2026-10-26. Sources below are first-party MariaDB Server or MariaDB Connector/Python documentation. Repository context: Connector/Python `1.1.14`, SQLGlot `30.24.0`; writes are currently disabled by default, the connection currently sets `autocommit=True`, and runtime authorization currently accepts only narrowly parsed scoped `SELECT`/`USAGE` grants and rejects active roles (`src/mariadb_mcp/connection.py`, `pyproject.toml`).

## Verified documentation facts

- **DML can be bounded at the statement level, but WHERE is not itself a safety bound.** MariaDB documents `UPDATE` and single-table `DELETE` with optional `WHERE`, `ORDER BY`, and `LIMIT`; without `WHERE`, each affects all rows. `LIMIT` limits rows updated/deleted. `INSERT ... VALUES` supports multiple value rows in one statement, and `INSERT ... SELECT` can source rows from other tables. [`UPDATE`](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/changing-deleting-data/update.md), [`DELETE`](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/changing-deleting-data/delete.md), [`INSERT`](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/inserting-loading-data/insert.md)
- **Syntax/version and replication caveats matter.** MariaDB documents `UPDATE ... LIMIT` as unsafe for statement-based replication. Multi-table `DELETE` gained `ORDER BY`/`LIMIT` only in 11.8.1; `UPDATE`/`DELETE` CTE forms are documented as available from 12.3; `UPDATE ... RETURNING` is documented from 13.0. [`LIMIT`](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/limit.md), [`DELETE`](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/changing-deleting-data/delete.md), [`UPDATE`](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/changing-deleting-data/update.md)
- **Affected-row counts are not always “matched rows.”** Connector/Python's `Cursor.rowcount` documents affected counts for `INSERT`/`UPDATE`/`DELETE`, with zero for no affected rows and `-1` when unavailable. MariaDB Server further specifies that `UPDATE` reports rows actually changed by default; `CLIENT_FOUND_ROWS` changes this to rows matched by `WHERE`. Cascaded/trigger side effects are not included in `ROW_COUNT()`. [`Cursor API`](https://mariadb.com/docs/connectors/mariadb-connector-python/api/cursor.md), [`ROW_COUNT()`](https://mariadb.com/docs/server/reference/sql-functions/secondary-functions/information-functions/row_count.md)
- **Connector transactions are explicit unless autocommit is enabled.** Connector/Python defaults `autocommit` to false; `Connection.begin()`, `commit()`, and `rollback()` are available (begin since 1.1.0). Its API warns rollback does not work as expected with autocommit enabled or a non-transactional storage engine; closing with uncommitted changes performs an implicit rollback. MariaDB Server states that data-change rollback depends on transactional storage and that DDL/admin statements can implicitly commit. [`Connector transactions`](https://mariadb.com/docs/connectors/mariadb-connector-python/transactions-with-mariadb-connector-python.md), [`Connection API`](https://mariadb.com/docs/connectors/mariadb-connector-python/api/connection.md), [`START TRANSACTION`](https://mariadb.com/docs/server/reference/sql-statements/transactions/start-transaction.md), [`ROLLBACK`](https://mariadb.com/docs/server/reference/sql-statements/transactions/rollback.md)
- **Locks depend on transaction and engine semantics.** InnoDB `SELECT ... FOR UPDATE` locks selected rows only when autocommit is off or the SELECT is inside a transaction; locks are released at commit. Under autocommit it has no effect for InnoDB. MariaDB also documents metadata locks held for tables used in a transaction until transaction end. [`FOR UPDATE`](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/for-update.md), [`Metadata Locking`](https://mariadb.com/docs/server/reference/sql-statements/transactions/metadata-locking.md)
- **Write grants can be object- and column-scoped, and required privileges differ by operation.** MariaDB supports global/database/table/column grant scopes. INSERT requires `INSERT`; UPDATE requires `UPDATE` on changed columns and `SELECT` for columns read; DELETE requires `DELETE` and `SELECT` on columns read in its conditions. [`GRANT`](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant.md), [`UPDATE`](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/changing-deleting-data/update.md), [`DELETE`](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/changing-deleting-data/delete.md)
- **`SHOW GRANTS` is not universally a complete effective-privilege inventory.** It lists grants for the named user or role; `SHOW GRANTS` without `FOR` means the connected account. MariaDB documents that grants applying through another account with the same username and a matching host can be absent from the connected account's `SHOW GRANTS` output. Roles may be enabled as the current role (including automatically on connect via a default role); `SET ROLE` changes current privileges. From 10.11, `PUBLIC` grants apply to all users; from 13.1, `DENY` lines are hidden from users lacking `SELECT` on `mysql`. [`SHOW GRANTS`](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/show/show-grants.md), [`GRANT` account matching](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant.md), [`SET ROLE`](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/set-role.md)

## Design recommendations (inferences, not MariaDB guarantees)

1. Preserve explicit opt-in per operation/table/field and build only single-table, single-operation DML from validated identifiers plus bound values. Treat SQLGlot parsing as syntax support, not authorization; reject unsupported forms rather than accepting broad MariaDB DML grammar. In particular, avoid `INSERT ... SELECT`, multi-table DML, `IGNORE`, upsert, and `RETURNING` unless separately specified and tested.
2. Require a supported transactional engine (for example, InnoDB) for writes that promise all-or-nothing behavior. Use a dedicated non-autocommit transaction for each request, commit only after policy checks, and rollback on errors or rejected outcomes. The current runtime's `autocommit=True` connection cannot provide the intended rollback workflow; avoid changing shared read-only behavior as an incidental side effect.
3. For update/delete caps, enforce a positive configured cap in the generated DML itself, and design the “would exceed cap => no partial changes” path around a transaction and measured rowcount. A conservative pattern is to execute with a cap-plus-one guard, rollback if the count exceeds the cap, otherwise commit; verify exact rowcount semantics and concurrency on the supported Connector/Python/server combination. Do not pre-count with an unlocked SELECT and assume the count remains valid. If exact-match limits rather than actual changed-row limits are required, document/test the `CLIENT_FOUND_ROWS` behavior or use a concurrency-safe selection strategy.
4. Keep the policy bounded to single-table DML: `LIMIT` can bound UPDATE/DELETE, but an update limit has a replication caveat and server behavior is version-sensitive. Pin/test supported MariaDB server versions, storage engines, and binlog mode; don't rely on syntax features merely because SQLGlot 30.24 parses them.
5. Treat `SHOW GRANTS` output as evidence, not proof of all effective privileges. Keep rejecting active/default roles and role grants unless role expansion is deliberately implemented; separately account for PUBLIC grants, host-matched grants, and server-version-specific DENY visibility. Current parser's scoped-SELECT-only rule is appropriate for the existing read-only mode but will reject INSERT/UPDATE/DELETE grants, so write authorization needs an explicit operation-aware policy/parser and negative tests—not a broad relaxation of the current regex.
6. Test counts for insert, update-to-different-value, update-to-same-value, no matches, delete cascades/triggers, constraint failures, cap boundary/cap+1, rollback, deadlocks/lock timeouts, and concurrent matching rows. Report driver DML `rowcount` as affected rows (not a universal count of matched logical records), and do not claim success when commit/result status is uncertain.

## Source/version note

The Connector/Python API pages are maintained as current documentation and include some 2.0-only material; the statements above use documented general Connection/Cursor semantics, while the project pins 1.1.14. Validate any behavior relied on in integration tests against that exact connector and the minimum/maximum supported MariaDB server versions. MariaDB documents `Connection.begin()` as available since 1.1.0, but that alone does not establish every behavior for every backend engine.
