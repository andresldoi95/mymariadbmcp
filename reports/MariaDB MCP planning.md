# Build a narrow, layered MariaDB boundary

The implementation should be a native Python 3.11+ MCP subprocess using the official MCP Python SDK v2 and MariaDB Connector/Python 1.1 GA, with STDIO as its only v1 transport. Its security boundary must combine a dedicated non-root account with narrow MariaDB `SELECT` grants, explicit object allowlists, whole-query AST validation and authorization, bound values, and enforced time and output budgets; neither MCP annotations nor a connector `read_only` option can replace those controls. V1 should expose only permission-aware metadata discovery, a deliberately constrained read-only query surface, and non-executing `EXPLAIN` analysis, rejecting uncertain or unsupported SQL rather than trying to accommodate it. This baseline prioritizes stable, auditable behavior and cross-platform native execution over an unproven newer connector or broad SQL compatibility. The key unresolved implementation risks are MariaDB-versus-MySQL parser semantics, complete metadata grants, and whether driver/server timeout behavior actually stops in-flight work. Recommendations below are distinguished from documented facts, and the release/version evidence reflects the research snapshot dated 2026-10-25.

## A GA connector trades easier packaging for predictable deployment

The project constitution requires Python, the official MCP Python SDK, MariaDB Connector/Python, and native Windows, Linux, and macOS support without Docker as a runtime requirement. **Set the product floor at Python 3.11 and use the official SDK v2 API, pinning the tested SDK release (2.3.0 is the research-date candidate).** The SDK's repository documents Python 3.11+, while PyPI metadata says `>=3.10`; Python 3.10 reached end-of-life on 2026-10-01, so choosing 3.11 resolves the conflict conservatively rather than treating package installability as support policy. Test the supported 3.11–3.14 matrix on each OS; do not claim 3.15 until the SDK package's support/test matrix is explicit. The v2 API is breaking from v1, which makes an exact tested pin and the v2 `MCPServer`/tool API important for reproducible client behavior. ([SDK repository](https://github.com/modelcontextprotocol/python-sdk); [SDK PyPI metadata and release history](https://pypi.org/project/mcp/); [Python version status](https://devguide.python.org/versions/); [SDK migration guide](https://py.sdk.modelcontextprotocol.io/migration/))

For database access, **prefer the latest stable 1.1 connector release identified in the notes, `mariadb==1.1.14`, and make MariaDB Connector/C 3.3.1+ an explicit platform prerequisite**. Connector/Python 1.1 is GA, but always uses its C extension and requires Connector/C; these installation costs are the price of selecting the stable GA line. Connector/Python 2.0 offers a pure-Python mode and bundled binary wheels that simplify installation, but the cited official docs still label 2.0.0rc2 a release candidate and advise against non-GA production use. Evaluate 2.0 separately after GA and verify every OS, architecture, and Python ABI rather than inferring a support matrix from “common platforms.” The 1.1 docs also conflict on Python minimums (guide: CPython 3.9–3.14; install prerequisite: Python 3.8), so lock and validate the precise release metadata and wheels in native CI. ([Connector/Python guide](https://mariadb.com/docs/connectors/mariadb-connector-python/mariadb-connector-python-guide); [installation](https://mariadb.com/docs/connectors/mariadb-connector-python/install); [installation prerequisites](https://mariadb.com/docs/connectors/mariadb-connector-python/install#c-extension-build-prerequisites))

**Use `mcp.run()` with its default STDIO transport and keep stdout exclusively for MCP wire messages.** MCP STDIO is newline-delimited UTF-8 JSON-RPC; logs belong on stderr and the process should exit on stdin EOF. Keep tool registration deterministic and separate standard `tools/list` discovery from database catalog-discovery tools. Use typed, bounded input/output models, and expose read-only annotations only as advisory client hints. Map expected errors to sanitized tool failures; SDK error forwarding and traceback logging mean raw exceptions or SQL details must not leak through either the client message or logs. This native subprocess architecture avoids a listening port and defers HTTP/network surface expansion, matching the feature spec and constitution. ([MCP STDIO transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio); [MCP tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools); [SDK tools](https://py.sdk.modelcontextprotocol.io/servers/tools/); [SDK error handling](https://py.sdk.modelcontextprotocol.io/servers/handling-errors/); [SDK logging](https://py.sdk.modelcontextprotocol.io/handlers/logging/))

## Layer database grants beneath application authorization

**Use a dedicated, non-root, host-scoped MariaDB account with only the required `SELECT` grants, and keep the application allowlist narrower than or equal to those grants.** MariaDB supports database-, table-, and column-level `SELECT`; `SHOW TABLES` visibility is filtered by privileges, while global `SHOW DATABASES` reveals all databases. A practical starting grant is `GRANT SELECT ON appdb.* TO 'mcp_ro'@'trusted-client-host'`, narrowed to tables or columns as the use case demands. Do not grant `FILE`, `EXECUTE`, `PROCESS`, `SUPER`, `READ_ONLY ADMIN`, grant option, or broad `SHOW DATABASES` merely for convenience; do not treat server `read_only` or the connector's `read_only` option as a substitute for least privilege. If connecting remotely, explicitly require TLS and certificate verification: Connector/Python 1.1's C extension defaults TLS and verification off, and MariaDB supports host-scoped accounts with `REQUIRE SSL`. ([MariaDB GRANT](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant); [SHOW TABLES](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/show/show-tables); [SHOW DATABASES](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/show/show-databases); [CREATE USER](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/create-user); [Connector/Python TLS parameters](https://mariadb.com/docs/connectors/mariadb-connector-python/api/connection#ssltls-parameters))

**Implement catalog discovery against the account-visible scope and a configured database/schema/table/column allowlist.** Prefer `information_schema` metadata and privilege-filtered table listings; expose only fields needed for the spec's columns, keys, indexes, and relationships. A global list of databases is not necessary to satisfy permission-aware discovery and could disclose unrelated names. The notes establish sources for table and column metadata but no single canonical grant recipe for every index, constraint, relationship, or view query. Therefore, add privileges only when tests show a specific required discovery query needs them; validate metadata completeness against each supported server version and report partial visibility as such. The conservative v1 recommendation is to exclude views unless their definitions and transitive dependencies can be safely resolved, because MariaDB views can execute under `DEFINER` context and reference other views, tables, joins, and functions. ([Information Schema COLUMNS](https://mariadb.com/docs/server/reference/system-tables/information-schema/information-schema-tables/information-schema-columns-table); [SHOW TABLES](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/show/show-tables); [CREATE VIEW](https://mariadb.com/docs/server/server-usage/views/create-view); [Connector/Python research notes](../research_notes/MariaDB%20MCP%20planning/mariadb_connector.md))

## A parser is a gate, not a proof of safe SQL

**Use a pinned SQLGlot release with its explicit MySQL dialect as the Python parsing baseline, behind an adapter that positively recognizes only supported syntax.** SQLGlot offers maintained MySQL parsing and traversable ASTs, but it describes its parser as intentionally lenient and not a validator; the dialect is MySQL, not version-specific MariaDB. Treat parse errors, unknown AST nodes, ambiguous name resolution, stale/incomplete metadata, or unsupported MariaDB syntax as rejection. Differentially test the exact parser/server versions and review AST changes on upgrades. TiDB's parser is a credible MySQL-compatible alternative for a Go implementation, but Go conflicts with the constitution's Python/official Python SDK requirement and does not remove MariaDB dialect risk. ([SQLGlot repository](https://github.com/tobymao/sqlglot); [SQLGlot MySQL dialect](https://sqlglot.com/sqlglot/dialects/mysql.html); [TiDB parser README](https://github.com/pingcap/tidb/blob/master/pkg/parser/README.md); [TiDB parser quickstart](https://github.com/pingcap/tidb/blob/master/pkg/parser/docs/quickstart.md))

The safe v1 query contract should be **one positively identified `SELECT` statement, plus a separately constrained `EXPLAIN [FORMAT=JSON]` wrapping the same authorized `SELECT`**. Reject writes, DDL, administration, multi-statements, `SELECT ... INTO`, file functions, user/system variables, assignment, locking clauses, `PROCEDURE`, stored routines/UDFs, unreviewed functions, `ANALYZE`, `EXPLAIN` variants that can execute or inspect another connection, and views unless recursive dependency authorization is implemented. MariaDB's `SELECT` grammar includes file output, variable assignment, row locks, and cross-database references; executable comments can contain SQL executed by MariaDB, so rejecting only obvious keywords or stripping comments before validation is unsafe. Use a MariaDB-aware lexer/token check to reject comment tokens (including executable comments) while preserving literal/identifier semantics, then parse and execute exactly the validated text—never validate one normalized string and run another. Parameter-bind values; identifiers cannot be parameter markers and must be resolved against trusted scope. ([MariaDB SELECT](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/select); [comment syntax](https://mariadb.com/docs/server/reference/sql-statements/comment-syntax); [PREPARE](https://mariadb.com/docs/server/reference/sql-statements/prepared-statements/prepare-statement); [FOR UPDATE](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/for-update); [CREATE FUNCTION](https://mariadb.com/docs/server/reference/sql-statements/data-definition/create/create-function); [EXPLAIN](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/analyze-and-explain-statements/explain))

Authorization must traverse every query scope, not just the outer projection: all tables and columns in joins, nested queries, each UNION arm, CTE definitions, correlated references, predicates, ordering, grouping, and function calls. Resolve aliases and derived outputs back to underlying authorized columns; reject unresolved or ambiguous names. When column restrictions apply, reject `*` unless it can be expanded from authoritative metadata and every expanded column checked. Fix the connection's default database, reject `USE`, and deny system schemas by default. This is application policy on top of database grants, not something the parser or MCP `readOnlyHint` promises. ([MariaDB SELECT](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/select); [CTEs](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/common-table-expressions); [GRANT column privileges](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant); [MCP tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools))

## Enforce budgets while admitting cancellation uncertainty

**Require explicit connection, query, row, and serialized-byte bounds, with cursor/connection cleanup on every path.** Connector/Python documents `connect_timeout`, socket/read/write limits, `query_timeout`, context managers, and buffered or streaming cursors; however, its docs do not establish identical `query_timeout` support across implementations or guarantee that a client timeout cancels server execution. `Connection.kill()` requires elevated privileges inappropriate for this read-only account. MariaDB's `max_statement_time` is a useful server-side backstop, but documentation says it is checked at execution checkpoints and can exceed the configured time. Apply a trusted server-side deadline that clients cannot override, test it with every pinned driver/server combination, and treat disconnect/timeout as potentially still-running work until observed behavior proves otherwise. Avoid granting kill privileges for cancellation. ([Connector timeout parameters](https://mariadb.com/docs/connectors/mariadb-connector-python/api/connection#timeout-parameters); [cursor buffering](https://mariadb.com/docs/connectors/mariadb-connector-python/api/cursor#cursorbuffered-bool); [connection kill](https://mariadb.com/docs/connectors/mariadb-connector-python/api/connection#connectionkillconnection_id-int-none); [MariaDB statement time limits](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/query-optimizations/query-limits-and-timeouts))

Use explicit cursor buffering behavior rather than relying on a documented default that conflicts between the cursor API parameter listing and example. For small bounded results, buffered fetching is simpler; for potentially larger bounded results, streaming and fetch-at-most-limit-plus-one can control application memory, but a row/byte output cap alone does not cap scan cost or prove the server stopped producing. Enforce execution deadlines and a hard server-side/result cap; do not blindly rewrite arbitrary SQL to add `LIMIT`, since UNIONs, ordering, and nested queries complicate semantics. Initially prefer request-scoped connections and cursors over a pool until concurrency measurements justify the added lifecycle surface. ([Connector cursor API](https://mariadb.com/docs/connectors/mariadb-connector-python/api/cursor); [MariaDB SELECT](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/select); [MariaDB EXPLAIN](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/analyze-and-explain-statements/explain))

The plan should use **pytest for offline unit tests and Ruff for lint/format**, with optional environment-gated live integration tests against a disposable or pre-provisioned database. Unit tests should exercise parser/authorization, bounds, sanitized errors, and MCP behavior without connecting to MariaDB. Integration tests should use a separate setup identity if fixtures create state, then exercise the runtime read-only identity; Docker can be one provisioning choice but not a requirement. Native install/startup/client smoke tests on Windows, Linux, and macOS are required evidence for portability. The research does not provide a defensible numerical latency or memory SLO, so the plan should not invent one: define configurable conservative limits and acceptance tests first, then set numeric defaults from an agreed workload. ([pytest skipping](https://docs.pytest.org/en/stable/how-to/skipping.html); [pytest fixtures](https://docs.pytest.org/en/stable/how-to/fixtures.html); [constitution](../.specify/memory/constitution.md); [Spec](../specs/001-mariadb-mcp-server/spec.md))

## Conclusion

The strongest implementation plan is intentionally narrower than a general SQL gateway: a local, pinned, native MCP process with independently enforced database and application boundaries, plus a SQL subset the team can explain and adversarially test. The less certain parts—metadata grant completeness, parser semantics, and in-flight cancellation—are not solved by adding more dependencies or privileges; they should become explicit fail-closed constraints and test gates. Before implementation, settle concrete row/byte/time defaults and the supported MariaDB version matrix, then verify those policies on each native platform without relaxing the constitution's least-privilege requirements.
